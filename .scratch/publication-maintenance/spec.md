# Publication 清理调度修复方案

Status: complete

日期：2026-09-10。当前基线：`66f11c6db9f43184f685773d3847047b29041a52`。
实现、隔离验证、main 集成、显式迁移与生产发布均已完成；25 分钟采样达到验收目标，详见 [验收记录](release-verification.md)。

## 目标与依据

让研究计算使用服务器算力，让清理成为有固定资源预算、可以恢复的后台维护工作。

已确认的生产证据见 [诊断记录](../../.local/rustfs-diagnosis-20260910/diagnosis.md)：6 个空闲 Worker 同时扫描 Publication 前缀；一次扫描返回 6,600 个对象、7 页、1,820,330 bytes，耗时 4.822 秒，符合清理条件的孤儿为 0。暂停这些 Worker 后，RustFS 从 1.880 核降到 0.043 核，恢复后升至 1.490 核。研究、批量、跟踪、刷新和明确删除队列均无待处理工作。

问题入口是 `entrypoints/worker.py` 的空闲轮询以及 `publication/service.py` 的 `collect_one_orphan` / `find_orphan_sha256s`：先全量发现，再最多删除一个对象。五秒休眠与一小时对象年龄阈值都没有限制扫描范围或跨进程重复工作。这段逻辑在 2026-08-24 已存在。

## 推荐结构

新增一个独立的 `publication-maintenance-worker`，使用现有 Core 镜像和 PostgreSQL / RustFS 依赖，只初始化 Publication 维护需要的资源。默认一个副本，支持误启动第二副本时仍然只有一个执行者。

维护容器的初始资源配置为上限 0.5 CPU、256 MiB 内存，必须通过最终镜像启动和满页测试。该限额约束维护进程本身；RustFS 的资源消耗仍由请求预算控制并实测验收。

Research、Batch Research、Tracking Worker 移除自动 Publication 清理调用。Tracking 工作缓存、Batch 本地 attempt 文件清理仍由各自模块负责，避免混淆本地执行文件与已发布对象。Data Operator 的刷新职责保持独立。

业务模块继续在释放最后一个引用时写入现有 `publication.object_deletions`。维护进程分别处理两种工作：

| 工作 | 意义 | 默认预算 |
|---|---|---|
| 明确删除队列 | 产品已经明确释放的对象 | 最短间隔 5 秒；一次最多处理 10 个队列项 |
| 孤儿发现 | 上传成功但没有完成数据库记录的遗留对象 | 最短间隔 60 秒；一次最多读取 1 页、1,000 个对象；最多删除 10 个孤儿 |
| 全轮扫描结束 | 已经检查完当前对象前缀 | 完成后至少等待 60 分钟再开始下一轮 |

每次维护步骤另设 10 秒合作式工作预算，到期不再发起新请求。正在进行的请求按当前显式 S3 超时结束；因此这是“工作预算 + 最后一个有超时请求”的界限，不承诺严格十秒返回。沿用有界重试，不在失败后紧密循环。

两类工作有独立的持久化到期时间，每次选择最早到期的一项，失败退避互不阻塞，避免持续的删除队列饿死孤儿扫描。初版使用模块常量，不增加用户设置页或通用任务调度框架。

在当前 6,600 个对象、没有孤儿的规模下，一轮约需 7 个维护步骤、6–7 分钟，再休息 60 分钟。扩大数据规模会拉长整轮耗时，单步请求和客户端内存预算保持不变。该方案接受垃圾回收延迟，不改变研究结果的可用时间。

## 协调、分页与恢复

### 单一执行权与持久化状态

增加 Publication 自己的维护状态表，记录两类工作的下次运行时间、失败次数，以及孤儿扫描的最后处理键、扫描开始时间、固定年龄截止时间和最近完整扫描结束时间。

复用 PostgreSQL advisory lock 的技术，使用一个独立的 Publication 维护锁。执行步骤必须在持锁数据库连接上完成控制事务；必要时为现有 `_postgres` 工具增加可以在持锁连接内执行事务的窄接口。不能只用进程内计时器或依赖 Compose 的副本数量，也不引入 Redis 或另一套租约系统。

维护锁覆盖一个有界步骤。扫描与普通查询不持有现有 Publication mutation 锁；只有单个对象的删除复查事务持有 mutation 锁，事务结束即释放。连接断开后停止本步骤，不能悄悄换连接继续推进。另一个维护进程取得数据库释放的锁后，按持久化进度继续。

### 按最后处理键推进

采用单次 `ListObjectsV2(Prefix=..., MaxKeys=1000, StartAfter=last_processed_key)`，不用自动遍历全部页的 paginator。返回必须满足合法前缀、严格递增、不超过上限、能向前推进等条件；异常页停止本步骤并告警，不回到无限全量扫描。

S3 普通 bucket 的字典序、`StartAfter` 和 `MaxKeys` 契约见 [官方接口](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html)。当前 RustFS 镜像的实际支持、删除后的续读及重启后的续读必须通过真实依赖测试；这是发布前置条件，不能仅凭 S3 兼容声明认为已经验证。

只查询本页 hash 是否已经记录，例如 `WHERE sha256 = ANY(...)`，不再每次读出整个 `publication.objects` 表。

游标只推进到已经判定完成或删除成功的最后一个对象：

- 命中时间或删除数量预算时，保存最后处理键，后面的对象留给下一步骤。
- 不能把“收到整页”当成“整页处理完”；否则会跳过未处理的孤儿。
- 空页结束本轮；非截断页只有全部处理完才结束本轮。
- 新增对象如果落在游标之前，由下一轮发现。按轮固定年龄截止时间，避免扫描过程中不断追赶新上传。
- 如果删除成功后进程在保存游标前崩溃，恢复可能重查一小段；缺失对象按幂等成功处理。没有确认成功的删除不得越过。

`MaxKeys` 限制返回数量，不保证 RustFS 内部只访问相同数量的文件；后端 CPU / I/O 成本仍以镜像测试和部署采样验收。

## 删除安全与失败处理

保留现有安全边界：只处理 Publication 对象前缀；孤儿必须早于本轮开始前一小时的截止时间；在 mutation 锁内再次查数据库，已经记录或重新有引用的对象不得删除。对孤儿候选在删除前复查当前对象元数据，已重新上传变新的对象跳过；数据库、元数据或权限检查不能确认时不删除。

不把扫描发现直接当作删除授权，不批量跳过引用复查，也不把孤儿塞进带 `publication.objects` 外键的明确删除队列。

分别持久化错误退避：首次失败至少等 1 分钟，再次失败延长为 2、4、8 分钟，上限 15 分钟；成功后清零。失败保留最后确认的进度，停止发起后续删除。权限错误、缺 bucket、非前进分页等输出明确失败码，避免静默成功。

数据库与 S3 仍不是一个原子事务；删除响应丢失等不确定结果通过同键幂等重试及引用复查处理。保留现有 Publication 发布/上传授权契约，新增并发回归验证，不宣称仅靠对象年龄就能保护所有正在发布的内容。

## 数据库迁移与发布

新增状态表需要下一次显式迁移。沿用现有版本化迁移入口：固定 SOURCE / TARGET 指纹，检查真实表结构，记录迁移结果。新安装 schema 与升级后的结构一致。

迁移仅增加维护元数据，保留已有 Research、Result、对象记录和 Dataset Head。验证旧数据升级、失败时 DDL/指纹一起回滚、重复执行，以及显式反向迁移。反向迁移前导出新增维护状态，业务数据不回退；迁移历史记录回退事件。

发布顺序：

1. 在隔离 worktree 完成实现与对应测试，集成到 main，在 main 复跑必要检查。
2. 从 main 合并到 `codex/contabo-deployment` 并推送。
3. 预检服务、队列、数据指纹；备份数据库及部署配置并验证备份。
4. 安排短维护窗口，排空工作并停止相关 Core 写入进程；运行显式迁移。
5. 启动新 Core 服务及单副本维护进程，验证 schema、健康和资源限额。
6. 采样完整扫描和休息阶段，保留数据一致性、CPU 和扫描计数证据。

若仅新清理进程异常，可以先停止它，研究服务继续运行，暂时允许垃圾积累。若必须回退整个 Core，停止相关进程、执行验证过的反向迁移，再启动旧镜像；不能在新 schema 上直接启动拒绝该指纹的旧程序。旧版会恢复原有高频扫描，应将其作为故障回退而非最终方案。

## 验证与完成标准

先补能抓住实际问题的失败回归，再实现：多空闲 Worker、对象量超过一页、没有待清理对象时，业务 Worker 不得进行对象列表扫描。维护步骤必须遵守可观察的单页、时间和删除预算；扩副本不放大扫描频率。

真实 PostgreSQL + 当前 RustFS 镜像验证：

- 两个维护进程争用、进程退出和数据库连接丢失后的接管。
- 超过一页、预算中断、游标键被删除、插入游标前后的对象、重启续读和最终完整覆盖。
- 无孤儿、有多个孤儿、失败恢复；删除成功但响应/游标提交丢失后的幂等。
- 发布/重新引用与删除并发，年轻对象保护，错误或不前进的列表拒绝，已有结果仍可读取。
- 明确删除与孤儿发现互不饿死；一类失败不阻断另一类。
- 真实旧数据库迁移、失败回滚、重复执行、反向迁移与恢复后运行。

复用仓库隔离集成入口，定向运行 Publication / Worker / migration 测试及 lint/typecheck。构建最终镜像，先做 image smoke；本次涉及维护进程恢复和部署边界，再运行 image qualification。发布分支与 main 按仓库规则验证，不使用开发数据卷。

生产验收使用此次已验证的采样方式：

- Research / Batch / Tracking Worker 的自动 Publication LIST 请求为 0。
- 无错误时，孤儿扫描最多每分钟一页；休息期无扫描。扩副本仍受同一个全局预算约束。
- 以约 20–30 分钟、覆盖当前一轮及休息段的空闲样本检查资源；初始目标是 RustFS 平均低于 0.2 核，允许单页请求期间短峰值。目标需实测，不预先保证固定百分比收益。
- 记录扫描条目、页耗时、删除/跳过数、完整扫描年龄、明确删除队列最老等待时间和错误退避。不要打印对象键、凭证或业务内容。
- 至少一次受控 Research → Result 可读链路通过；前后 Dataset Head 和已有成功结果不受影响，不能仅凭 CPU 降低宣布完成。
- 有持续积压时，对比本轮与上轮进度及队列年龄；维护容量不足明确报出，不通过取消预算回到无限扫描。
