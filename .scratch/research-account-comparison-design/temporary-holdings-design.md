# 临时每日持仓：按读取续期，到期清理，按当前数据重跑

Status: needs-triage

> 这是临时持仓边界的补充说明；本轮已发布 [正式规格](spec.md)，统一状态为 ready-for-agent，不再以本文的阶段状态要求确认。

2026-09-12。用户明确提出：每日持仓可以随回测保存，但一段时间未读取/排障后删除；以后需要时直接重跑，不要求使用原数据版本，接受结果存在差异。该方向已纳入 [三种能力设计](three-capabilities-design.md)。本稿先采用 **7 天未读取过期** 的实施默认值；7 天由本轮建议选定，并非用户指定的期限。产品实现尚未修改。

## 保存边界

| 内容 | 保留方式 |
|---|---|
| 原 ResearchRun 指标、每日净值、账户汇总和冻结配置 | 按既有 Result 生命周期保留 |
| 回测终端状态、Track 已发布检查点及必要持仓/现金/目标 | 按既有续算与发布规则保留，不受排障明细期限影响 |
| 已确定保存的目标、模拟订单/成交及业务事件 | 保持三种能力设计中的事件结果合同 |
| Daily Holding Observations | 每日实际逐股持仓与当时估值，作为可过期的独立诊断产物保存 |

正常 Strategy Backtest 执行时就生成每日持仓，不等 Agent 请求后才第一次重算；Factor Evaluation 不生成账户持仓。Track 只生成本次新增 Session 的明细。空仓 Session 也记录覆盖范围，区分“该日确实空仓”和“该日明细不可用”。

明细直接记录该次实际执行的股票、数量、估值、实际权重和所需账户信息，标明 Open 观察时点；不要在读取原明细时改用最新行情重新估值。只保存实际持有的股票，不保留全 Universe Alpha/Label 面板、表达式树或逐算子日志。

## 7 天闲置期限

一个成功 Run 的临时持仓是一个保留单元；Batch 按子 Run 分开；DailyTrack 按每次成功 Advance 的新增明细分开。新的 Run、Batch 中其他子 Run 完成，或 Track 新的 Refresh，都不会给旧明细自动续期。

```text
expires_at = max(published_at, last_successful_detail_read_at) + 7 days
```

- 初始期限从对应结果/新增段成功发布时算起，不从回测研究日期或任务排队时刻算起。
- Agent/MCP 或网页成功读取尚未过期的持仓明细后，对实际读取的保留单元续期 7 天。合法空仓日期的明细读取也算；只请求状态、摘要、列表或到期时间不算。
- 后台轮询、预取状态、健康检查和垃圾回收自身不续期；网页实际打开持仓明细时才发起数据读取。
- 到期后返回 `expired` 和清理/到期信息，不以空数组冒充空仓，不因访问过期元数据而复活产物。需要再生成时提交新的回测。
- 日期过滤和分页属于同一保留单元的读取。持续使用的单元会续期；这不是永久存储承诺，也不需要首版再增加多档保留套餐或永久保留开关。

首次写入使用有界 Chunk/批次和压缩列式文件，不在内存中积累整段十年持仓再序列化。正常运行增加的写入和临时磁盘峰值仍需计入资源预算；TTL 解决历史持续累积，不能使单次产物或峰值免费。

## 与 Result 独立发布、清理

ResearchRun / DailyTrack Module 管理临时明细的拥有者、状态、来源执行、覆盖区间、最后读取时间和到期时间；字节使用现有 RustFS 与序列化能力。它不是永久 Result/Checkpoint 校验所必需的分区，不能在到期后使原 Result 缺少必需对象、读取失败或 Track 无法续算。

有效数据内容发布后不变；可变的是诊断产物的可用性和保留期限。新保留策略只适用于明确标记为临时的产物，不把已有永久 Result 数据悄悄改为可删除。

清理复用已有维护与 Publication 删除流程：先原子确认到期并撤销该临时产物的拥有引用，再让现有引用检查删除无其他引用的对象。不能对共享对象桶按创建时间直接删除，也不能删除仍被 Result、Checkpoint 或其他产物引用的字节。读取、续期与清理须协调同一个元数据状态，防止有效读取期间被删除；物理删除失败保留重试状态，不恢复已过期查询。

逻辑到期和后台物理清理分开：过期即不再作为可读取明细，磁盘由周期性维护回收；清理不要求精确在某一秒完成。暂存失败、取消及进程中断的未发布分区沿用有界清理规则，不暴露为完整成功的诊断记录。

## 过期后按当前数据重跑

用户已接受数据版本可能不同，重跑不以找到旧 Generation、旧引擎或与旧净值完全一致为准入条件。采用当前应用合同和本次准入的 Data Generation，复用原策略、模拟参数与研究区间，提交一个普通的新 Strategy Backtest；不增加第三种 Research Kind 或精确重放服务。

同一次新 Run 内仍固定数据与计算身份，保证自身计算一致。记录 `source_run_id` 等来源关系及新旧实际数据/规则身份，不自动修改原策略规则以凑出旧收益。旧输入若在当前合同下不合法，返回正常配置诊断，不暗加旧版本执行路径。

新的每日持仓属于新 Run，界面及 MCP 标明“当前数据重新回测”，并提供原 Run 的关联。新旧指标可供查看，但差异不导致该次重跑失败，也不设置“必须相同”的校验门槛。不能把新明细混进原 Run 的原始持仓分区，或覆写旧指标来表示补齐成功；也不承诺数据修订的影响一定很小。

对 Track 的历史排障，同样另建当前数据下的普通回测，按来源策略及所选覆盖范围从对应原始研究起点运行；不修改 Track 的已发布账户，也不把原已发布状态与新数据重跑结果拼成同一条原始历史。正常 DailyTrack Refresh 仍从自己的完整已发布状态继续；放宽跨 Run 的结果一致性不改变这条续算合同。

读取过期明细不会隐式发起计算。网页的“重新回测生成持仓”操作，或 Agent 显式调用已有提交能力，创建新 Run 并正常排队、计预算、支持取消；无需为了数据版本变化另加一次确认。新的运行再次按本规则保存和续期明细。

## 网页与 MCP

- 永久结果仍显示指标、净值与期末/当前持仓；新增“每日持仓”诊断视图，有效期内按日期、股票分页读取，显示原执行身份、覆盖范围及保留至时间。
- `get_research_run_result` / `get_daily_track_result` 在目标合同中增加临时持仓 section。返回 `available`、`expired`、`not_recorded` 等明确可用性；冻结内容的 cursor 绑定实际产物和来源执行，期限到达后返回过期，而非悄悄切到别次运行。
- 可用性摘要和实际明细读取分开，避免工具轮询本身续期。读取不启动回测；重跑沿用 `submit_research_run(research_kind="strategy_backtest", ...)`，来源关联是元数据，不改变输入语义。工具字段及枚举需按实施后的正式 Schema 发布，以上不是当前已可调用接口。
- 过期视图保留原指标与净值，提示“每日持仓已过期，可用当前数据重新回测”。重跑后链接到新的 Run，并明确新明细不保证与原运行一致。

## 当前代码接缝和验收

[Strategy](../../apps/core/src/thesistrace/research_kernel/strategy.py) 已有可选 ledger，包含每日 positions、cash、NAV 及交易信息；[主 Chunk 路径](../../apps/core/src/thesistrace/research_kernel/research_chunks.py) 还没有将它作为独立临时产物输出。应复用同一计算核心并补有界收集、临时发布与分页读取，不复制交易循环。

[Publication](../../apps/core/src/thesistrace/publication/service.py) 现有删除流程会复核对象是否仍被 manifest 引用，可复用其引用安全；[Data 生命周期](../../apps/core/src/thesistrace/data/lifecycle.py) 的输入 pin 与临时持仓期限是两件事，不为持仓保留窗口额外永久钉住旧行情数据。

实施时通过公开接口验证：

1. 开启收集不改变同输入的账户、费用、目标、成交或终端状态，原运行明细在有效期内与其当时的计算相符。
2. 完成、首次读取、续期、到期、空仓、分页、状态轮询不续期；使用可控时间，不靠真实等待 7 天。
3. 真实依赖下验证并发读取与清理、删除重试、共享引用保护；原 Result 和 Track 续算在诊断过期后仍完整可用。
4. Batch 子 Run 与 Track 新增段的期限独立，查询一个单元不会给整组或全部追踪历史续期。
5. 过期后用当前已发布数据提交新 Run，允许其与原结果不同；原数据版本缺失不构成重跑障碍，原结果不被覆盖。
6. 量测单次及批量的压缩字节数、写入耗时、峰值内存和清理滞后；未读取部分的稳定占用约为保留窗口内的产量，再加仍被使用的单元与待清理字节，而非所有历史 Run 的累计量。

本轮只更新设计和 ADR，没有开启实际定时清理、删除数据、提交线上重跑或修改运行代码。
