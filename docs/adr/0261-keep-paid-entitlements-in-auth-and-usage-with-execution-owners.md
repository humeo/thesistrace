# Keep paid entitlements in Auth and usage with execution owners

The Auth, Core, and Agent ownership boundary below is accepted and implemented; real merchant Test Mode payment-flow verification remains pending. The user has selected Creem with monthly billing in USD, replacing the earlier CNY requirement. This currency and interval are supported by Creem's current [Create Product contract](https://docs.creem.io/api-reference/endpoint/create-product); merchant eligibility and end-to-end payment behavior still require verification.

Creem is authoritative for payments and billing, Auth owns the Researcher-to-subscription association and Paid Plan Entitlement, and Core and Agent retain ownership of their resource usage, settlement, and admission decisions. Browser and MCP operations consume the same entitlement contract, preserving the identity and ownership boundaries in [ADR-0233](0233-separate-better-auth-identity-from-core-research-authorization.md) and [ADR-0241](0241-keep-operator-authority-split-between-auth-and-core.md). The proposed integration reuses the official Creem SDK, hosted Checkout, and customer portal for invoices, payment methods, and cancellation; the application controls plan changes.

Creem changes its billing product immediately, including when a no-proration downgrade leaves the current period's payment intact. Auth therefore retains the confirmed paid-period entitlement separately from the product selected for renewal, so the Researcher can use the purchased plan until expiry while the next bill uses the lower plan. Reliable payment evidence creates or extends that entitlement; a browser return, active status, or changed product alone cannot grant additional paid usage. Entitlement remains associated with its supporting payment so that a confirmed full refund or payment dispute affects the corresponding rights without revoking rights supported by other valid payments. Billing changes preserve daily consumption and outstanding reservations, and a temporary Creem outage preserves already-confirmed rights through their paid end. This accepts an explicit local entitlement model to keep billing transitions from silently changing research ownership, resetting usage, or prematurely removing purchased capacity. The downgrade sequence is an application-level inference from [Creem's documented behavior](https://docs.creem.io/features/subscriptions/managing) and requires Test Mode verification, including failed upgrade payments and renewal races.

Billing event projection, reconciliation, dispute resolution and manual negative acknowledgement reuse the existing Auth operation coordinator to hold a Researcher session advisory lock while reading Creem. No database transaction remains open during provider requests. Once the evidence is available, a short transaction atomically updates the verified inbox, account and payment projections. This preserves serialization with billing commands without extending PostgreSQL idle transaction limits; connection failure uses the coordinator's existing guarded release path.

Agent writes each ended provider call's known cost or final unknown-cost absorption to a local durable settlement outbox before updating PostgreSQL. The outbox uses the existing Node runtime's [SQLite API](https://nodejs.org/download/release/v24.14.0/docs/api/sqlite.html), with [FULL synchronous writes](https://www.sqlite.org/pragma.html#pragma_synchronous), on a persistent Agent volume; it contains reservation identifiers and amounts, never prompts. PostgreSQL remains the only quota ledger. Failed writes are retried, new admission waits for pending settlement, and the single Agent host replays known decisions before absorbing reservations whose calls were interrupted by the prior host's exit. This follows the existing single-host Run recovery boundary; backups and restores must retain this volume with the PostgreSQL data.
