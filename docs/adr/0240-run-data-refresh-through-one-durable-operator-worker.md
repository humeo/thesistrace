# Run every Data Refresh through one durable Operator Worker

Both the Operator Console and private CLI submit Market, Financial, and Industry Refreshes to one global FIFO as durable Data Refresh Operations, and one single-slot Data Operator Worker serially claims and executes them. Accepted work may be cancelled before claim; running and terminal receipts are immutable, and Retry creates a new key. Every claim uses a 15-minute renewable lease with a 30-second heartbeat, reconciles a publication that completed before a crash, and retries infrastructure loss on the same operation at most three times before `RETRY_EXHAUSTED`, while business rejection remains terminal and Financial pending or gaps remain degraded success. Submission remains available while the Worker is unavailable because PostgreSQL is the durable boundary, and terminal receipts remain for 180 days without retaining their Data Generations. This hard-cuts the current split between queued Market work and synchronous one-shot Financial or Industry commands so HTTP returns after acceptance, every operation has one lifecycle and recovery boundary, and Head-writing paths cannot consume upstream capacity concurrently; the Worker alone owns the deployment Tushare Secret, and the design rejects long-running HTTP execution, per-kind Workers, duplicate CLI implementations, automatic scheduling, and a combined Refresh action.
